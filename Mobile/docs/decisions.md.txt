## Architecture

### Pattern: MVVM + Repository

```
Fragment / Activity
    ↓  observes LiveData
ViewModel  (AndroidViewModel)
    ↓  calls
Repository
    ↓  calls
ApiService  (Retrofit interface)
    ↓  HTTP
Node.js Backend  (:3000/api/)
```

Fragments own no business logic. They only:
1. Inflate layout via ViewBinding
2. Pass user events to ViewModel methods
3. Observe LiveData and update views

ViewModels own state and call repositories. They never reference Android views or
Fragments directly.

Repositories call `ApiService`, wrap callbacks with `MutableLiveData`, and return
`LiveData<T>` to ViewModels.

---

### Navigation: Single Activity per context

- `SplashActivity` — launcher, routes after 1.8s
- `AuthActivity` — hosts Login / Register / OTP fragments (not yet using NavComponent)
- `MainActivity` — hosts all main-app fragments via Jetpack NavComponent + `nav_graph.xml`
- Bottom navigation menu IDs (`homeFragment`, `productListFragment`, etc.) match
  fragment destination IDs in `nav_graph.xml` exactly — required for `NavigationUI`
  to highlight the correct tab

Cross-fragment navigation uses `Navigation.findNavController(view).navigate(R.id.dest, args)`.
Safe Args is NOT used — arguments are passed via `Bundle` manually.

---

### Application class: `UniFurnitureApp`

The `Application` subclass holds and exposes the `ApiService` singleton.
ViewModels access it via `UniFurnitureApp.getInstance().getApiService()`.

There is **no dependency injection framework** (no Hilt, no Dagger).
All dependencies are wired manually in ViewModel constructors.

---

### API Configuration

The base URL is set at build time via `local.properties`:

```
# local.properties
api.base.url=http://192.168.x.x:3000/api/
```

It is injected into `BuildConfig.API_BASE_URL` and consumed by `ApiClient`.
The emulator default is `http://10.0.2.2:3000/api/`.
Never hardcode an IP address — always use `local.properties`.

## Coding Conventions

### File naming
- Java classes: `PascalCase` (e.g., `ProductListFragment.java`)
- Layout XML: `snake_case` mirroring class name (`fragment_product_list.xml`,
  `item_product_card.xml`, `activity_main.xml`)
- Drawable: `ic_` prefix for icons, `bg_` for backgrounds, `placeholder_` for
  placeholder images

### ViewBinding
All layouts use ViewBinding (`buildFeatures { viewBinding true }`).
- Fragments: inflate in `onCreateView`, null in `onDestroyView`
- Pattern:
  ```java
  private FragmentHomeBinding binding;

  public View onCreateView(...) {
      binding = FragmentHomeBinding.inflate(inflater, container, false);
      return binding.getRoot();
  }

  public void onDestroyView() {
      super.onDestroyView();
      binding = null;
  }
  ```

### ListAdapter + DiffUtil
All RecyclerView adapters extend `ListAdapter<T, VH>` with an inner `DiffUtil.ItemCallback`.
Use `submitList()` to update data — never call `notifyDataSetChanged()` directly.
Current implementations use only `_id` equality for `areContentsTheSame`; update
this if fine-grained diff is needed.

### LiveData pattern in Repositories
Repositories wrap Retrofit callbacks in `MutableLiveData` and return `LiveData`:
```java
public LiveData<ProductDto> getProductDetail(String slug) {
    MutableLiveData<ProductDto> result = new MutableLiveData<>();
    apiService.getProductBySlug(slug).enqueue(new Callback<ProductDto>() {
        public void onResponse(...) { result.setValue(...); }
        public void onFailure(...)  { result.setValue(null); }
    });
    return result;
}
```
On failure, repositories post `null` — ViewModels and Fragments must null-check before use.

### ViewModel LiveData observation
ViewModels use `observeForever` when chaining repository calls inside the ViewModel
itself (not recommended long-term but consistent throughout the project — do not
deviate). Fragments observe with `getViewLifecycleOwner()`.

### String IDs in DTO
MongoDB `_id` fields are mapped with `@SerializedName("_id") public String id;`
across all DTOs. Always use `.id` in code — never `._id`.

### Currency formatting
Always use `FormatUtil.formatCurrency(Double)` — never format VND manually.
It handles null (returns "Liên hệ") and formats with dots as thousands separator.

### Discount badge
Always use `FormatUtil.discountBadge(minPrice, compareAtPrice)` — returns null if
no discount, returns `-XX%` string if discounted. Check for null before setting visibility.

## Implementation Constraints

### Room is declared but unused
`androidx.room:room-runtime:2.6.1` is in `build.gradle` but no `@Database`,
`@Dao`, or `@Entity` classes exist yet. It was declared "for offline cart cache"
in a comment. Do not use Room in the Discovery scope (Home/ProductList/Detail) —
those screens fetch live data only.

### No auth header on API calls
`ApiClient` does not attach a `Bearer` token header. Current API endpoints in the
Discovery scope (products, categories, collections, reviews) are public and do not
require auth. Cart/wishlist endpoints need `customer_id` as a query param instead
of a header. This is consistent with existing usage — do not add an auth interceptor
unless an endpoint returns 401.

### Product rating is not a direct filter param on the API
The `GET /products` endpoint does not accept a `minRating` query param based on
current `ApiService` definitions. A rating filter on the ProductList screen must
be applied client-side (filter the returned list in the ViewModel) unless the
server endpoint is extended. Confirm with backend owner before adding a server param.

### `observeForever` memory leak risk
ViewModels use `observeForever` for chained calls (e.g., `loadProduct` triggers
`loadImages`, `loadVariants`, `loadReviews`). This is an existing pattern in the
project — follow it for consistency, but be aware it can cause leaks if the
ViewModel is not cleared. Do not add new `observeForever` calls in Fragments.

### Deprecated back navigation
`ProductDetailFragment` calls `requireActivity().onBackPressed()`, deprecated
since API 33 (Android 13). The minimum SDK is 26 so it still compiles, but the
replacement is:
```java
requireActivity().getOnBackPressedDispatcher().onBackPressed();
```
Fix this when touching `ProductDetailFragment`.

### `ProductListFragment` has no inline search bar
Search only reaches `ProductListFragment` via navigation arguments from Home.
If a user lands on Products via the bottom nav tab, there is no way to search
from within that screen. A search `EditText` or `SearchView` in the toolbar of
`ProductListFragment` is needed to fully satisfy the Search requirement.

### `ImageSliderAdapter` does not use `DiffUtil`
It uses plain `notifyDataSetChanged()` in `updateImages()`. This is fine for the
image slider (small, replaced all at once) — do not change this adapter, but do
not use this pattern in new adapters.

### `AuthActivity` was missing its initial fragment transaction
`AuthActivity.onCreate()` called `setContentView()` but never showed any fragment,
resulting in a blank white screen. Fixed by adding:
```java
if (savedInstanceState == null) {
    getSupportFragmentManager()
        .beginTransaction()
        .replace(android.R.id.content, new LoginFragment())
        .commit();
}
```
All auth fragment navigation (Login → Register → OTP) uses `android.R.id.content`
as the container — the initial transaction must use the same container for consistency.

### VMware on host machine breaks Android emulator's `10.0.2.2` routing
On machines with VMware installed, the standard emulator shortcut `10.0.2.2`
(which normally maps to host's `localhost`) times out. Root cause: VMware's virtual
network adapters (`VMnet1`, `VMnet8`) interfere with QEMU's virtual network routing.

**Workaround confirmed working (2026-05-31):**
Set `api.base.url` in `Mobile/local.properties` to the host machine's WiFi adapter IP:
```
api.base.url=http://192.168.1.12:3000/api/
```
Find the correct IP with `ipconfig` — use the `IPv4 Address` under `Wireless LAN adapter Wi-Fi`,
not any VMware adapter. This IP changes when the network changes, so each team member
must set their own value. `local.properties` is gitignored — never commit it.

`adb reverse tcp:3000 tcp:3000` also works as an alternative but resets on every
emulator restart; the WiFi IP approach is more stable for development.

### Server `POST /api/auth/login` had two API mismatches with the mobile app
Discovered 2026-05-31 during first login test. Two issues:

**Issue 1 — Field name:** App sent `{"phone": "..."}`, server expected `{"emailOrPhone": "..."}`,
causing a `400 Information required` response.

**Issue 2 — Response format:** Server returned `{ message, profile }`, but the app's
`AuthViewModel` checks `response.token != null` and `LoginFragment` calls
`session.saveCustomer(result.customer)`. Without `token` and `customer` keys, login
appeared to fail silently.

**Fix applied to `server/src/controllers/auth.controller.js`:**
- `login()` now reads `emailOrPhone || phone` so both field names are accepted
- Successful login returns `{ token: profile._id, customer: { _id, name, phone, email } }`

**Note:** The `token` is currently the MongoDB `_id` string — not a signed JWT.
This is sufficient for development and guest-mode testing, but Khải should replace
it with a proper `jsonwebtoken`-signed token before the project is demoed, since
`SessionManager` uses the token presence to determine login state.

## Technical Recommendations

### 1. Banner slider: reuse CollectionDto.bannerUrl
`HomeViewModel` already calls `getCollections()` and exposes `getCollections()`
LiveData. Use the Collection items' `bannerUrl` field as banner images. Reuse
`ImageSliderAdapter` directly (do not subclass) + `ViewPager2` + `Handler`
auto-scroll loop. Full decision record is in the "Feature Decisions" section below.

### 2. Filter bottom sheet: use Material BottomSheetDialogFragment
Create `FilterBottomSheetFragment extends BottomSheetDialogFragment`. Pass the
current filter state in via a static factory method. Communicate selected filters
back to `ProductListFragment` via a shared ViewModel scoped to the Activity, or
via a listener interface. Do not use Fragment result API here — the ViewModel
approach is consistent with the rest of the project.

### 3. Pagination: append, do not replace
`ProductListViewModel` currently replaces the `products` LiveData on every load.
For pagination, maintain a running `List<ProductDto>` in the ViewModel and
merge pages:
```java
List<ProductDto> allProducts = new ArrayList<>(current);
allProducts.addAll(newPage.items);
products.setValue(new ApiListResponse<>(allProducts, newPage.total));
```
Detect end of data with `allProducts.size() >= total`.

### 4. Real-time search: Handler debounce
In `HomeFragment.onQueryTextChange`, post a delayed `Runnable` (300ms) to the
main `Handler`. Remove pending callbacks on each new keystroke before posting the
new one. Navigate to `ProductListFragment` only on submit; for autocomplete,
show results inline in a `RecyclerView` beneath the search bar.

### 5. Grid/List toggle: swap LayoutManager
Keep a boolean `isGrid` in `ProductListFragment`. On toggle:
```java
binding.rvProducts.setLayoutManager(
    isGrid ? new GridLayoutManager(requireContext(), 2)
           : new LinearLayoutManager(requireContext()));
adapter.notifyDataSetChanged();
```
The same `ProductCardAdapter` works in both modes — the card width is fixed at
160dp which fills a grid cell well but may look odd in list view. Consider a
separate `item_product_list.xml` for full-width list rows.

### 6. Quantity selector: standalone layout component
Add a `+/-` row to `fragment_product_detail.xml` between the variant chips and
the bottom bar. Track quantity as an `int` local field in the Fragment (not in
the ViewModel — it is transient UI state). Pass it to `viewModel.addToCart`.

### 7. Recommendations: extend ProductDetailViewModel
Add a `MutableLiveData<List<ProductDto>> recommendations` field.
After `loadProduct` resolves, call:
```java
productRepo.getRecommendations(slug, userId).observeForever(recommendations::setValue);
```
`getProductRecommendations` in `ApiService` already returns `Map<String, List<ProductDto>>` —
extract the `"recommendations"` key from the map.

## Navigation Conventions

### Bundle navigation over Safe Args

**Decision:** All cross-fragment navigation uses `Bundle` + `Navigation.findNavController().navigate(R.id.dest, bundle)`. Safe Args is not used.

**Why:**
- The initial scaffold (Khải Đào, commit `17e9ba3`) established Bundle navigation throughout. Every call site — `HomeFragment` (search, category tap, "View All"), `ProductDetailFragment` (back button) — uses `getArguments().getString("key")` to read args.
- Safe Args requires the `androidx.navigation.safeargs` Gradle plugin and generates a `*Directions` class per destination. Introducing it mid-project would require migrating all existing navigation call sites or mixing two patterns in the same codebase — both options add churn with no functional gain for this project's scope.
- For this project (student demo, single developer per feature scope, no deep link requirements), Bundle navigation is fully sufficient.

**Rule:** Always add new navigation arguments to `nav_graph.xml` as declared `<argument>` elements even when using Bundle navigation. This keeps the nav graph as the authoritative record of what arguments a destination accepts, even though the declarations have no runtime effect without Safe Args.

### [P1 #1] Home: Banner / Image Slider

**Date recorded:** 2026-05-31
**Status:** ✅ Completed 2026-05-31 — manually tested, all 8 items passed

---

#### Decision: Reuse `ImageSliderAdapter` without modification

**What was decided:** Use `ImageSliderAdapter` exactly as it exists today. Do not
create a subclass (`BannerAdapter`) and do not modify the existing class.

**Why:**
- `ImageSliderAdapter` already does exactly what the banner needs: it accepts
  `List<String>` image URLs and renders each as a full-bleed `CENTER_CROP`
  `ImageView` inside a `ViewPager2`. The `updateImages(List<String>)` method
  refreshes data correctly.
- It is already proven working in `ProductDetailFragment` for the product image
  slider — the same layout pattern (ViewPager2 inside a fixed-height FrameLayout
  with DotsIndicator overlay) is used there verbatim.
- Creating a subclass would introduce a parallel class with identical behaviour,
  violating the project rule "avoid duplicate implementations" (see `decisions.md`
  Rules section).
- The adapter creates `ImageView` instances programmatically, so there is no layout
  XML to change — only `fragment_home.xml` and `HomeFragment.java` are touched.

**Trade-off acknowledged:** Because `ImageSliderAdapter` creates plain `ImageView`s
with no layout file, it is not possible to add a text overlay (e.g., collection
name) to each banner slide without modifying the adapter. This is acceptable for
the current task. If text overlays are required in a future iteration, the approach
would be: create `item_banner.xml` (ImageView + TextView), change `onCreateViewHolder`
to inflate it, and add a parallel `updateBanners(List<CollectionDto>)` method.

---

#### Decision: Extract `bannerUrl` list in the Fragment, not the ViewModel

**What was decided:** The Fragment (`HomeFragment`) filters `CollectionDto` items
to a `List<String>` of non-null `bannerUrl` values and passes that list to the
adapter. The ViewModel is not changed.

**Why:**
- The ViewModel already exposes the full `ApiListResponse<CollectionDto>` via
  `getCollections()`. Adding a second LiveData for banner URLs alone would duplicate
  state unnecessarily.
- URL extraction (`c.bannerUrl != null && !c.bannerUrl.isEmpty()`) is a view-layer
  concern — it determines what to *display*, not what to *store*.
- The same `getCollections()` observer will be reused for the Collections section
  (P1 #2), which needs the full `CollectionDto` objects (id, name, slug). Keeping
  one observer that feeds both the banner and the collections row minimises API
  calls and code duplication.

---

#### Decision: Implement auto-scroll with `Handler` + `Runnable`, not `Timer`

**What was decided:** Use `new Handler(Looper.getMainLooper())` with a self-posting
`Runnable` for the 3.5-second auto-scroll cycle.

**Why:**
- `Handler` posts to the main thread directly — no `runOnUiThread` wrapper needed.
- `Timer` / `ScheduledExecutorService` run on background threads; updating
  `ViewPager2.setCurrentItem()` from a background thread causes a
  `CalledFromWrongThreadException`.
- `Handler.removeCallbacks(runnable)` is the correct, well-documented cancellation
  mechanism and integrates cleanly with the Fragment lifecycle.
- This is the conventional Android pattern for auto-scrolling banners and requires
  no additional dependencies.

---

#### Lifecycle management for auto-scroll — rules and rationale

The `Handler` + `Runnable` pair must be managed across three Fragment lifecycle
events. Failing to do so causes either a memory leak or a `NullPointerException`
after `binding` is set to null in `onDestroyView`.

| Lifecycle event | Action | Reason |
|---|---|---|
| `onViewCreated` | Create `Handler` and `Runnable`; do NOT post yet | Adapter has no data yet; posting before data loads wastes cycles |
| After `bannerAdapter.updateImages(urls)` | `handler.postDelayed(runnable, 3500)` | Only start after data is confirmed present and count > 1 |
| `onPause` | `handler.removeCallbacks(runnable)` | Fragment is backgrounded (user switches apps or receives a call); scroll should stop |
| `onResume` | `handler.postDelayed(runnable, 3500)` if `count > 1` | Fragment returns to foreground; scroll resumes |
| `onDestroyView` | `handler.removeCallbacks(runnable)` | View is destroyed on navigation; `binding` will be null on next `Runnable` fire without this guard, causing NPE |

**Critical constraint:** The `Runnable` references `binding.bannerViewPager` to
call `setCurrentItem`. If `onDestroyView` nulls `binding` before `removeCallbacks`
is called, the next `Runnable` fire crashes. `removeCallbacks` must always be
called before `binding = null`.

**Correct `onDestroyView` order:**
```java
public void onDestroyView() {
    super.onDestroyView();
    if (autoScrollHandler != null) {
        autoScrollHandler.removeCallbacks(autoScrollRunnable);  // ← before null
    }
    binding = null;  // ← after removeCallbacks
}
```

**`onResume` guard:**
```java
public void onResume() {
    super.onResume();
    if (bannerAdapter != null && bannerAdapter.getItemCount() > 1) {
        autoScrollHandler.postDelayed(autoScrollRunnable, 3500);
    }
}
```
The `bannerAdapter != null` guard handles the case where `onResume` fires before
`onViewCreated` has set up the adapter (e.g., after process restore).

#### Decision: Fix `GET /categories` and `GET /collections` to return `List<T>` not `ApiListResponse<T>`

**Discovered:** 2026-05-31 during banner testing (categories and banner both blank)

**Root cause:** Both server controllers (`getAllCategories`, `getAllCollections`) return
a plain JSON array `[...]`. The Android `ApiService` declared
`Call<ApiListResponse<CategoryDto>>` / `Call<ApiListResponse<CollectionDto>>`, which
expects `{ items: [...], total: N }`. Gson threw a `JsonSyntaxException` silently →
`onFailure` called → LiveData set to `null` → nothing rendered.

**Fix applied:** Changed return types to `Call<List<T>>` in `ApiService`,
`LiveData<List<T>>` in `ProductRepository`, `MutableLiveData<List<T>>` in
`HomeViewModel` and `ProductListViewModel`.

**Why not fix the server instead:** The web admin's `AdminCollections` component
does `this.collections = data` expecting a raw array. Wrapping the server response
in `{ items, total }` would break the admin UI. The mobile-side fix is the safer
change with zero cross-team impact.

**Rule going forward:** Before adding a new `ApiService` endpoint that returns a
list, check the actual server response shape with Postman first. Do not assume all
list endpoints return `ApiListResponse`.

#### Decision: Banner UI polish — gradient overlay + styled DotsIndicator + disk cache

**Date:** 2026-05-31

**Gradient overlay:**
Added a 60dp `View` with `bg_banner_gradient.xml` (transparent → 33% black, top to
bottom) anchored to the bottom of the banner `FrameLayout`. This ensures dots remain
readable against any banner image without darkening the full slide.

**DotsIndicator styling:**
- `app:dotsColor="#80FFFFFF"` — inactive dots: 50% white
- `app:selectedDotColor="@color/accent"` — active dot: `#D4A853` gold (confirmed
  correct attribute name for `dotsindicator:5.0`; `dotsSelectedColor` does NOT exist
  in this version and causes a resource-linking error)
- `app:dotsSize="5dp"` / `app:dotsSpacing="3dp"` — smaller and tighter than library
  defaults (8dp / 4dp) for a cleaner look on the 200dp banner

**Glide disk cache:**
Added `diskCacheStrategy(DiskCacheStrategy.ALL)` to `ImageSliderAdapter.onBindViewHolder`.
This caches both the original and transformed (centre-cropped) bitmap to disk.
After the first network load, subsequent app opens show banner images instantly
without waiting for a network round-trip. Applies to all `ImageSliderAdapter` usages
(home banner and product detail images).

### [P1 #2] Home: Collections Section

**Date recorded:** 2026-06-01
**Status:** ⚙️ Implemented 2026-06-01 — awaiting manual test

---

#### Decision: Follow `CategoryAdapter` pattern exactly for `CollectionAdapter`

**What was decided:** `CollectionAdapter` is a structural copy of `CategoryAdapter`:
`ListAdapter<CollectionDto, VH>` + inner `DiffUtil.ItemCallback` + inner
`OnCollectionClickListener` interface + `ViewBinding` in the ViewHolder.

**Why:**
- `CategoryAdapter` is the only existing horizontal-list adapter for entity cards in
  this project. It is proven working (categories render correctly on Home). Deviating
  from its structure for collections would introduce two inconsistent patterns in the
  same adapter package with no benefit.
- `ListAdapter` + `DiffUtil` is the project-wide convention for all RecyclerView
  adapters (documented in `decisions.md` "ListAdapter + DiffUtil" section). Using it
  here maintains that consistency.
- The `OnClickListener` as an inner interface (rather than a lambda in the Fragment) is
  consistent with `CategoryAdapter`, `ProductCardAdapter`, and `ReviewAdapter`. All
  three use the same interface pattern.

**One structural difference from `CategoryAdapter`:** `CollectionAdapter` constructor
accepts an additional `String serverHost` parameter. This is required because
`CollectionDto.bannerUrl` is stored as `http://localhost:3000/uploads/...` by the
server and must be rewritten to the actual host before Glide can load it on the
emulator. The rewrite pattern (`url.replace("http://localhost:3000", serverHost)`) is
identical to the one already in `HomeFragment`'s banner observer. `serverHost` is
computed once in `HomeFragment.setupRecyclerViews()` as
`BuildConfig.API_BASE_URL.replace("/api/", "")` and injected at construction time.

**Why not rewrite in the Fragment before `submitList()`:** `submitList()` takes
`List<CollectionDto>` — the DTO objects. Rewriting would require mutating DTO fields
in place (bad: DTOs are data-layer objects, not view-layer objects) or creating wrapper
objects (overkill for one field). Injecting `serverHost` into the adapter is the
minimal, clean solution.

**Why `CategoryAdapter`'s `category.imageUrl` does not need the same rewrite:**
`CategoryDto.imageUrl` is served from the same server but the emulator + WiFi-IP
workaround (`local.properties`) is already in effect for all API calls via `ApiClient`.
Category images load via the same base URL path. The `bannerUrl` specifically stores
the full `http://localhost:3000/...` origin URL (set by the upload middleware at
create/update time), which is why only `bannerUrl` needs rewriting.

### [Bug] BottomNavigationView Home Tab — Navigation 2.7.6 Multiple Back Stacks

**Date recorded:** 2026-06-01
**Status:** ✅ Fixed 2026-06-01

---

#### Symptom

Home tab in `BottomNavigationView` never responds to taps from any screen.
Products / Cart / Account tabs work. No crash. No application code modifies the
Home menu item at runtime. Appeared after P1 #1/P1 #2 made the navigation paths
more prominent, but the root cause predates those changes (original scaffold).

#### Working Theory: Navigation 2.7.6 `saveState`/`restoreState` Cycle

`NavigationUI.setupWithNavController` (Navigation 2.7.6) auto-enables multiple back
stacks. When any tab is tapped, `onNavDestinationSelected` builds:

```java
NavOptions options = new NavOptions.Builder()
    .setLaunchSingleTop(true)
    .setRestoreState(true)
    .setPopUpTo(graph.findStartDestination().id, false, /*saveState=*/ true)
    .build();
navController.navigate(item.getItemId(), null, options);
```

For Products / Cart / Account: navigate target ≠ `popUpTo` target (`homeFragment`).
`saveState` saves under key=target; `restoreState` looks up key=target. Different keys
→ normal behavior ✓.

For Home tab: navigate target (`homeFragment`) == `popUpTo` target (`homeFragment`).
Both save and restore use key=`homeFragment`. `popUpTo` saves the current stack under
key=`homeFragment`; `restoreState` immediately finds and restores that same state,
reverting the navigation. Net effect: zero visible change from every screen.

#### Proposed Fix (pending diagnostic confirmation)

Replace `NavigationUI.setupWithNavController` in `MainActivity.java` with a manual
`setOnItemSelectedListener` using plain `popUpTo` **without** `saveState`/`restoreState`:

```java
binding.bottomNavigation.setOnItemSelectedListener(item -> {
    NavOptions options = new NavOptions.Builder()
        .setLaunchSingleTop(true)
        .setPopUpTo(R.id.homeFragment, false)
        .build();
    try {
        navController.navigate(item.getItemId(), null, options);
        return true;
    } catch (IllegalArgumentException e) {
        return false;
    }
});
navController.addOnDestinationChangedListener((controller, destination, arguments) -> {
    Menu menu = binding.bottomNavigation.getMenu();
    for (int i = 0; i < menu.size(); i++) {
        MenuItem menuItem = menu.getItem(i);
        if (menuItem.getItemId() == destination.getId()) {
            menuItem.setChecked(true);
            break;
        }
    }
});
```

This removes the `saveState`/`restoreState` cycle while preserving:
- Correct back stack pop when switching tabs
- Visual tab highlighting on destination change
- `launchSingleTop` to prevent duplicate destinations

Only `MainActivity.java` changes. No nav_graph, fragment, or adapter changes.

#### Decision: Use `MaterialCardView` for `item_collection.xml`

**What was decided:** `item_collection.xml` uses `MaterialCardView` as the root, not
`LinearLayout` or plain `FrameLayout`.

**Why:** `item_product_card.xml` already uses `MaterialCardView` with
`cardCornerRadius="12dp"` and `cardElevation="2dp"`. Using the same root for collection
cards gives visual consistency (same rounded-corner, same elevation shadow) without
adding any new dependency — Material Components is already in `build.gradle`.

**Card dimensions:** 140dp wide × 90dp tall (landscape ratio, slightly wider than
category cards at 80dp, proportional to a banner image aspect ratio).
